# MDL 오류 L&L 관리

사용자가 말하는 MDL 관리 자동화 문제를 접수하고 해결방안을 조사하여 누적한다. 기본 저장소는 `https://github.com/wjdeotjd3902-ctrl/work-automation`, 기본 브랜치는 현재 저장소 메타데이터로 확인한다. 데이터 경로는 `MDL 관리 자동화/L&L`, 배포 스킬 경로는 `MDL 관리 자동화/skills/mdl-lessons-learned`다. 사용자가 다른 저장소를 명시하면 그 지시를 따른다.

## 진행

1. 저장소의 AGENTS.md와 L&L/README.md를 읽고 최신 원격 상태를 확인한다. 기존 기록을 오류 코드·증상·구분으로 검색한다. 같은 원인과 조건이면 기존 ID에 발생 이력을 추가하고, 원인이 불명확하거나 다르면 새 기록을 만들어 관련 ID를 연결한다. 과거 기억을 새 사용자 보고나 현재 검증 결과로 바꾸지 않는다.
2. 저장소의 `L&L/templates/lesson.md`를 사용한다. 없으면 설치된 [기록 양식](references/lesson.md)을 사용한다. 새 ID는 현재 한국 날짜와 그 날짜의 기존 최대 번호+1로 정하고 충돌을 확인한다. 파일은 `records/LL-YYYYMMDD-NNN.md`에 만든다. 미상 정보는 미상, 가설은 가설로 쓴다. 정보가 부족해도 접수부터 저장하고 조사에 꼭 필요한 질문 하나만 한다.
3. 관련 코드·설정·오류 근거를 먼저 조사한다. 외부 기술 사실이나 현재 제품 동작 확인이 필요하면 공식 문서·공식 이슈·원본 소스로 검색하고 URL과 확인일을 저장한다. 해결안은 적용 조건, 구체적 절차, 복구 방법, 검증 기준을 포함한다. 확인되지 않은 해결책은 제안으로 남긴다.
4. 실제 수정은 사용자 요청과 기존 승인 범위에서만 수행한다. L&L 기록 요청 자체는 원본 메일 이동·삭제, MDL 셀 변경, 예약 작업 재활성화의 허가가 아니다. 실제 환경 작업은 해당 작업 스킬을 확인하고 원본 보존 및 사전 계획·사후 확인을 따른다. 검증 수준과 실제 결과를 기록하고, 같은 가정으로 3회 실패하면 중단하여 의심되는 가정과 필요한 정보를 남긴다. 재발 방지안은 적용 범위를 명시하고 관련 스킬을 임의로 개정하지 않는다.
5. 기록과 README 목록을 함께 갱신한다. 상태는 접수/조사중/해결안 제시/적용완료/검증완료/보류/재발 중 하나다. 실제 검증 근거 없이 검증완료로 처리하지 않는다. 초기 0건 문구는 첫 접수 때 제거한다. 수정 이력은 보존하고 기존 사례를 삭제하거나 덮어 없애지 않는다.

## GitHub 저장과 확인

사용자는 이 데이터베이스에 향후 보고하는 MDL 문제와 해결안을 계속 저장하도록 요청했다. 그 범위의 익명화한 기록 저장에는 매번 승인을 되묻지 않는다. 공개 저장 전에 이름·이메일·프로젝트명·문서번호·메일 원문·내부 경로·토큰을 제거하고 기술적 의미가 유지되는 별칭을 사용한다. 익명화가 불가능한 자료는 업로드하지 않고 필요한 정보만 질문한다.

원격 연결·권한 문제 시 로컬 기록을 먼저 보존하고 `GitHub 미반영`을 명시한다. 연결 성공을 추정하지 않는다. 무관한 로컬 변경을 포함하지 않고 기록과 목록 파일만 명시적으로 커밋한다. 원격 충돌 시 최신 내용을 읽고 보존하여 합치며 force push는 하지 않는다. 전송 후 원격 커밋과 파일 내용을 다시 읽어 확인한다. 결과에는 ID, 현재 상태, 확인된 원인/제안, 검증 수준, GitHub 링크 또는 미반영 사유를 간단히 보여준다.

이 스킬은 대화에서 보고한 문제를 처리한다. 백그라운드 감시나 다른 대화의 자동 수집을 약속하지 않는다. 새 대화에서 자동 선택되지 않으면 `$mdl-lessons-learned`로 호출할 수 있다.
